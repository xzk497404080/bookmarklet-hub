抖音图文 · 需求挖掘台

在抖音网页版筛出图文帖，把评论里的问句聚成候选需求。数据只留在本机，跨帖子持续累积。

拖我到书签栏

按住红色按钮拖到浏览器书签栏松手。看不到书签栏按 ⌘⇧B（Windows Ctrl+Shift+B）。
代码约 ，全部可读，右键书签「编辑」能逐行看。

先看一眼成品

示例数据 · 不用登录 · 不发请求

下面嵌的就是真实面板，用 3 条图文帖、33 条模拟评论跑出来的。 可以切「问句 / 需求候选 / 原始评论 / 自检」几个页签看效果，导出按钮在示例模式下也能用。

1怎么用

  1. 浏览器里登录抖音网页版，用关键词搜一批内容（对比 / 避坑 / 求助型图文最好）。
  2. 搜索页点「筛选 → 内容形式 → 图文」（抖音自带），往下滚动把结果加载出来。
  3. 点一下书签，面板弹出。首屏 search/stream 是分块流、翻页是 search/single，两种响应都会解析，图文帖自动进本机池。
  4. 点开某条图文帖，在详情页再点一次书签，点「自动展开评论」——它会定位评论区、分段滚动，让页面自己发 comment/list 请求；按钮上显示实际触发的响应数。
  5. 换下一条帖子重复。数据按评论 ID + 文本去重，跨帖子、跨会话累积，不会被后一次覆盖。
  6. 回到任一页点书签，看「需求候选」。粗 / 细两档聚合粒度可切，导出 CSV 或复制 LLM 重构提示词。
采集三条路线兜底拦截响应（含分块流）→ React Fiber → DOM 正文
初筛问句 + 四型分类场景 / 疑虑 / 规格价格 / 吐槽将就
归并意图分桶 + 两档粒度粗看一类需求多热，细看具体场景差异
重构留给人或 LLM输出四字段，不假装自动产出需求

2为什么这么设计

不自己构造请求
a_bogus 由页面 SDK 实时算，改 aweme_id 就失效
只拦截页面自己的响应
签名、登录态、指纹全都是真的
UI 放在 srcdoc iframe
与页面同源，彻底隔离抖音的全局 CSS
原始层永不删减
清洗都在别的视图，随时回来复核

抖音 Web 的评论接口对纯 HTTP 免登录请求返回空体，游客态还有评论墙。 所以在自己登录态的页面里发请求是唯一稳的路线——这正好是书签脚本的主场。 工具不构造请求：自动展开只负责定位评论区 + 分段推进 + 派发滚动事件，请求仍由页面自己发。 它不会自动翻搜索下一页，也不会自动打开下一条图文帖，这两步得自己点。

这四层里，工具只负责前两层

采集池是「算法推给你的 + 愿意公开打字的 + 被原帖框架限定过的」。所有条目共享同一个前提， 再加一万条也降不掉这块偏差。要打它只能换信息源头：跨关键词、跨账号、跨时间窗， 再拿搜索下拉词、小红书同题、电商问答做对照。

「需求候选」不是需求。把问句变成需求是重构（触发场景 / 当前做法 / 具体阻力 / 期望结果）， 工具只做初筛和归并。另外，评论区挖出来的全是已表达需求，别人也在答，天然红海； 真正值钱的常在没被问出口的地方——抱怨、将就的做法、「我一般就…凑合」。
安全：纯前端，零后端、零服务器、零上报。请求是你自己的浏览器发的，cookie 从不离开本机； 数据存在 localStorage（dy_need_v1），换浏览器或清缓存就没了，重要的记得导 CSV / JSON。 整段代码约 110.9 KB。
